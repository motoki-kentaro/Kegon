# Internationalization (i18n)

Status: accepted (Issue #2)
Date: 2026-10-07

Kegon's own UI text is localized. Kegon ships with `en-US` and `ja-JP`.

## Library and format

Kegon uses [Fluent](https://projectfluent.org/) (`.ftl` files) through
[`fluent-bundle`](https://crates.io/crates/fluent-bundle), the core crate of
Project Fluent's Rust implementation.

- Fluent supports arguments (`{ $name }`), CLDR plural rules
  (`[one] … *[other] …`), and per-locale grammar without code changes.
- `fluent-bundle` is pure Rust and small. It is maintained by Project Fluent
  and used in Firefox.
- Higher-level crates such as `fluent-templates` and `i18n-embed` were not
  chosen. With two embedded locales they would mostly add macros, loaders,
  and dependencies Kegon does not need.

Supporting crates:

- `unic-langid` parses locale tags. It is already a dependency of
  `fluent-bundle`.
- `sys-locale` reads the OS's preferred UI languages. On Windows it calls
  `GetUserPreferredUILanguages`, with no other dependencies.
- `fluent-syntax`, as a dev-dependency only, lets tests list the messages in a
  resource.

## Resources

```text
assets/i18n/
├─ en-US.ftl   canonical; every message must exist here
└─ ja-JP.ftl
```

The files are embedded in the binary with `include_str!`, like the icons.
Nothing is read from disk at runtime, and no extra files need to be
distributed.

Each locale's resource is parsed once, at startup, when the `Localizer` is
created. Views only format messages that are already parsed.

## Architecture

```text
Workbench / domain state      stable enums and IDs (ActivityItem, TabId)
    ↓
UI (src/app.rs)               maps state to a MessageKey
    ↓
Localizer (src/i18n/)         formats the key for the active locale
    ↓
assets/i18n/*.ftl
```

- `src/i18n/` does not depend on iced.
- `Workbench` holds no display text. A test fails if string literals or i18n
  imports appear in the model code.
- `MessageKey` is an enum, one variant per message, so a typo in a key is a
  compile error. Each variant maps to its Fluent ID in one table in
  `src/i18n/key.rs`.

## Locale resolution

The locale is chosen once, at startup:

1. **Explicit request** (`--locale`). If it names a supported language, that
   locale is used. If it is unsupported or malformed, `en-US` is used, not
   the OS locale. An explicit request therefore gives the same result on
   every machine.
2. **OS preferred UI languages**, in order. The first supported one wins. For
   example, `fr-FR, ja-JP` resolves to `ja-JP`.
3. **`en-US`**, if nothing matched or the OS locale could not be read.

Tags are matched by language, after normalization:

- Case does not matter.
- `_` is treated as `-`.
- POSIX suffixes such as `.UTF-8` and `@modifier` are ignored.
- `ja`, `ja-JP`, and `ja_JP.UTF-8` all mean `ja-JP`.
- `en-GB` maps to `en-US`.

## Missing messages

| Situation | Result |
|---|---|
| Message exists in the active locale | The localized text |
| Message missing from `ja-JP` | The `en-US` text |
| Unsupported locale requested | `en-US` throughout |
| Message missing from `en-US` too | The message ID itself, e.g. `side-bar-git-title` |

The application never panics and never shows blank text because a message is
missing. In debug builds, every fallback is reported on stderr.

Missing messages are caught before they ship:

- Every `MessageKey` must exist in every locale, and every message in the
  resources must have a `MessageKey`. Tests fail on missing or unused
  messages.
- Resources must parse without errors. Debug builds assert this, and the
  tests run in debug.

The runtime fallback from `ja-JP` to `en-US` exists for robustness. The test
suite keeps `ja-JP` complete. If a future locale is maintained with partial
coverage, relax the completeness test for that locale only.

## Adding a UI string

1. Add the message to `assets/i18n/en-US.ftl`, then translate it in every
   other locale's file.
2. Add a variant and its ID to `message_keys!` in `src/i18n/key.rs`.
3. In the UI, call `localizer.text(MessageKey::…)`. For messages with
   arguments, call `localizer.text_with(key, &args)`.
4. Run `cargo test`. The completeness tests confirm the key and resources
   agree.

For counts, use Fluent plural selection rather than formatting numbers
yourself:

```ftl
changed-files = { $count ->
    [one] { $count } file changed
   *[other] { $count } files changed
}
```

Japanese has no grammatical plural: CLDR maps every count to `other`.

## Message ID conventions

- Use lowercase kebab-case: `area-element[-qualifier]`. Examples:
  `side-bar-git-title` and `terminal-new-tab-tooltip`.
- The first segment names the UI area: `activity`, `side-bar`, `terminal`,
  `main`, and so on.
- The `MessageKey` variant is the same name in PascalCase:
  `SideBarGitTitle`.
- Name messages after their role, not their English text, so the ID stays
  valid if the wording changes.
- Group messages by area in the `.ftl` files, using `##` section comments.

## What must not be localized

Only text that Kegon itself presents as UI is localized. These are not:

- Shell, terminal, and CLI tool output, including AI agent output
- Git data: commit messages, branch names, diffs, and file contents
- File system paths and file names
- Internal identifiers, command IDs, and configuration keys
- Command-line option names, such as `--locale`
- Log and debug messages
- The product name, **Kegon**
- Symbols used as icons, such as the `+` on the new-tab button

## Development locale override

```sh
cargo run -- --locale ja-JP
cargo run -- --locale en-US
kegon --locale=ja-JP
```

- If `--locale` is repeated, the last one wins.
- `--locale` without a value counts as an explicit request for an unsupported
  locale, so it gives `en-US`, and Kegon prints a warning.
- Unknown arguments are ignored with a warning.
- Warnings go to stderr and never stop Kegon from starting. Release builds on
  Windows have no console, so the warnings are not visible there.

## Future work

- A Settings UI will let users choose the locale. The choice will act as the
  explicit request in step 1 of the resolution order. Persisting it is out of
  scope for now.
- The locale is fixed for the lifetime of the process. Switching at runtime
  would mean replacing the `Localizer` held by the application state.
- UI and terminal fonts should be chosen explicitly. Today Japanese text uses
  per-glyph font fallback (see `gui-stack.md`).
